# Decisiones de implementación

Decisiones menores tomadas durante la construcción. Las contradicciones entre documentos que cambian el diseño se consultan antes.

## H0

- **pnpm 11.21** (instalado) fijado con `packageManager` (corepack). El plan decía 10.x; se usa la versión instalada por acuerdo.
- **Node 24** en `.nvmrc`, `engines` e imágenes (el documento de arquitectura decía 22; manda el plan).
- **Quién escribe `ts.lecturas`:** el documento de datos asigna el `INSERT` a `ingest` (tabla de consultas críticas). Se corrige: `ingest` valida, agrupa y encola; el `worker` hace el `INSERT` (flujo MQTT → cola → worker → Postgres del plan y requisito de `PUBACK` tras encolar).
- **Versiones fuera de la última mayor** por compatibilidad con el stack del plan: TypeScript 5.9 (no 7), Zod 3.25 con `fastify-type-provider-zod` 4.x (las 5+ piden Zod 4), pino 9, BullMQ 5.
- `ioredis` se usa como cliente de Valkey; es la dependencia que ya trae BullMQ, no una nueva pieza del stack.
- **Sin paso de build:** Node 24 ejecuta TypeScript con type stripping. Los imports llevan extensión `.ts`, `tsconfig.base.json` activa `allowImportingTsExtensions` y `erasableSyntaxOnly` (sin `enum` ni parámetros-propiedad), y los paquetes del workspace exportan su `src/`. El mismo código corre en desarrollo (`node --watch`), pruebas (Vitest) y producción. Por eso `tsx` (aprobado) no hace falta y no se instala. En la imagen no se usa `pnpm deploy` (Node no quita tipos bajo `node_modules`): se conserva el layout del workspace.
- **Contrato `telemetria`:** `.strict()` (rechaza campos desconocidos); las cinco mediciones son opcionales y admiten `null` (sensor caído, RF-39). Los rangos físicos no se validan en el contrato: un valor fuera de rango es señal de falla y lo evaluará `calidad` (H2).
- **Dynamic Security:** `mosquitto_ctrl dynsec init` crea el cliente administrador con acceso total (`#`) y `defaultACLAccess` permisivo. `mqtt-bootstrap` (idempotente, por la API `$CONTROL`) lo reduce al rol `admin` del documento de datos, deja `defaultACLAccess` en `false` y concilia roles y ACL: no borra roles, para no desasignarlos de clientes ya creados. Se agregó `unsubscribePattern` a `nodo`, `ingest` y `admin` (con el defecto en `false`, un cliente no podría anular suscripciones) y `publishClientReceive` de `$CONTROL/dynamic-security/#` para que `admin` reciba las respuestas. `addClientRole`/`addGroupClient` devuelven "Internal error" si ya existen, por eso se consulta `getClient` antes. Verificado contra Mosquitto 2.1.2: la sustitución `%u` funciona (un nodo no puede publicar en el tópico de otro; `ingest` recibe de todos).
- **Imagen de Mosquitto:** `eclipse-mosquitto:2.1.2-alpine` (existe `2.1` y `2.1.x` solo en variante alpine).
- **Usuario MQTT del proceso `api`:** el plan solo lista `MQTT_INGEST_*` y `MQTT_ADMIN_*`. `api` y `worker` publican como `lympha-control` (rol `control` del documento de datos), de ahí `MQTT_CONTROL_USER/PASSWORD`.
- **Valkey ACL:** BullMQ consulta `INFO` al conectar y `-@dangerous` lo bloquea; se agregó `+info` y `+@connection` a los usuarios `api`, `ingest` y `worker`. Verificado con BullMQ real: `api` no puede leer `bull:lecturas:*`.
- **`jobId` de BullMQ:** BullMQ rechaza `:` en ids personalizados, y el documento de datos proponía `deviceId:seq`. Además, con lotes agrupados un reenvío del broker produce un lote distinto, así que el `jobId` no podría deduplicar. La idempotencia queda solo en la base (`ON CONFLICT (nodo_id, ts) DO NOTHING`); los jobs no llevan `jobId`.
- **Postgres en Compose:** los ajustes se pasan como flags `-c` (no con `config_file`) para conservar el `shared_preload_libraries` que la imagen de Timescale escribe al inicializar. El archivado de WAL (pgBackRest) solo se activa en `prod.yml`.
- **Certificados de desarrollo:** CA propia generada por un contenedor `certs` de una sola ejecución (`alpine/openssl`), sin depender de mkcert ni de openssl en el host. La llave privada queda en un volumen; solo `infra/certs/ca.crt` (pública, ignorada por git) sale al host para el simulador.
- **Variables de desarrollo:** `infra/compose/dev.env` se versiona con valores obviamente de desarrollo y se carga con `env_file`, para que el comando `docker compose -f base.yml -f dev.yml up` funcione sin `--env-file`.
- **Migraciones `0000`–`0008` completas más `0009_perfiles_uso`** (acordado): el SQL sale del documento de datos. Cambios mínimos:
  - `0000_init` solo concede `USAGE` en los esquemas; extensiones, roles, contraseñas y esquemas los crea `infra/postgres/init-roles.sh` (idempotente, como superusuario), porque `CREATE ROLE ... PASSWORD :'pw'` es sintaxis de `psql`, no de un ejecutor de migraciones, y rotar contraseñas no debe depender de una migración.
  - `pgcrypto` y `citext` se instalan en el esquema `app`: el documento revoca `public` a todos y las funciones `SECURITY DEFINER` fijan `search_path = app, pg_temp`, así que `digest()` no se encontraría en `public`. TimescaleDB queda en `public` (no es reubicable) y solo `lympha_owner` tiene `USAGE` en él (su `search_path` incluye `public`).
  - **Hueco en el documento de datos:** con `FORCE ROW LEVEL SECURITY` el dueño también queda sujeto a RLS y las políticas están `TO lympha_app`, así que `mis_espacios()`, `es_propietario()` y `reclamar_nodo()` (todas `SECURITY DEFINER`, dueño `lympha_owner`) no verían ninguna fila. Se agrega una política `definer` para `lympha_owner` en cada tabla con RLS. El dueño no se usa desde la API. Verificado con pruebas de aislamiento.
  - `0009_perfiles_uso` carga los 4 perfiles con `config_wqi` marcador (`{"pendiente": true}`); las curvas reales son de H2. Es necesario porque `nodos.perfil_id` tiene FK.
  - No se incluyen todavía `app.siguiente_envio`, `app.quiere_aviso` (H3) ni las funciones `crear_espacio`, `desvincular_nodo`, `aceptar_invitacion`, `transferir_propiedad`, `eliminar_mi_cuenta` (H1); tampoco los trabajos `add_job` de mantenimiento ni `fillfactor` de `estado_nodo` (H1).
- **Ejecutor de migraciones propio** (`platform/migrar.ts`, ~60 líneas, sin dependencias nuevas) en lugar del migrador de drizzle-kit: aplica una transacción por archivo (como pide el documento de datos; el migrador de drizzle usa una sola para todo el lote), con bloqueo consultivo y registro en `app.migraciones`. Un archivo que empieza con `-- no-transaction` se ejecuta sin envolver. drizzle-kit queda para generar SQL de tablas relacionales futuras.
- **Drizzle** se usa como ejecutor tipado de transacciones con SQL explícito (`sql`) dentro de `conUsuario()`/`conSistema()`; el error real de Postgres viene en `error.cause` (Drizzle lo envuelve como "Failed query").
